# Именование веток

Формат: `frontend/[feature,bug,refactor]/name_of_feature_or_bug`

Примеры: 
```
frontend/feature/add_admin_page
frontend/bug/remove_page_tilt_on_swipe
```

- Почему так:
    - Мы работаем в монорепо, первая часть говорит куда направлены изменения (`frontend/...`)
    - Вторая часть отвечает за смысл ветки (`.../feature/...`)
    - Третья часть объясняет изменения (`.../.../name_of_feature_or_bug`)

# О коммитах 

Для быстрого определения того, какой импакт имеет конкретный коммит на проект, 
стараеимся придерживаться [conventional commits](https://www.conventionalcommits.org/en/v1.0.0/#summary)

## CheatSheet с примерами:

### Префиксы и их значения (от более частых к менее частым):
- `feat` - добавление новых функциональных возможностей
- `fix` - исправление ошибок

- `refactor` - изменение кода
- `style` - форматирование кода
- `docs` - документация
- `chore` - изменения не влияющие на функциональность (версии приложения, обновление тулзов итп.)

### Если коммит содержит BREAKING CHANGE:
- Добавить к префиксу ! `prefix!: description` 
- Либо в нижнюю часть коммита добавить `BREAKING CHANGE: description`

#### Пример:
```bash
chore!: drop support for Node 6

BREAKING CHANGE: use JavaScript features not available in Node 6.
```

# Общие советы

1. Делать коммиты чаще, локализовать изменения, не хранить всё под одним коммитом
2. Документировать код, смысл его существования и не очевидные моменты
3. Управлять зависимостями только с помощью `flutter pub` во избежания проблем version resolving
4. Используйте template при создании merge requests если они есть
